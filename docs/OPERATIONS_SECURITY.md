# 보안과 데이터 보존 운영 안내

코드 배포와 운영 환경 설정은 별도 작업입니다. 아래 확인은 각 기관의 운영 담당자가 실제 리소스와 계약을 기준으로 수행합니다.

## 배포 전 확인

1. 로컬·운영 관리자 암호를 직접 교체하고 설정 권한과 담당 사업 범위를 확인합니다. 신규 로컬 설치의 초기 암호는 무작위이며 기존 계정은 자동 변경되지 않습니다.
2. Azure App Service의 실제 `node -v`가 지원 LTS의 보안 패치 수준인지 확인합니다. GitHub Actions의 빌드 Node와 운영 런타임은 다를 수 있습니다.
3. HTTPS 전용, 최소 TLS 1.2 이상, DB·Blob 지역과 접근 권한을 확인합니다. 코드만으로 실제 Azure 리전이나 포털 설정을 확인할 수 없습니다.
4. AI 공급자·모델·예산 알림·사용 한도와 계약의 국가·보관·삭제 조건을 확인합니다. 공급자를 바꾸면 개인정보처리방침 초안을 갱신하고 기관 문안을 검토한 뒤 저장합니다.
5. `pnpm test`, `pnpm lint`, `pnpm audit --prod`를 실행합니다. Dependabot 제안은 검증 후 반영하며 자동 병합하지 않습니다. Docling 변경은 별도 컨테이너 빌드와 한국어 문서·표·스캔 PDF 변환 비교를 거친 뒤 수동 배포합니다.

## 상담 보존과 정기 삭제

상담기록은 생성 시각부터 365일을 기준으로 만료 대상을 삭제합니다. 새 상담 저장과 상담 목록 조회 때 실행하는 기존 삭제를 유지하며, `POST /api/maintenance`로 접속이 없는 날에도 삭제할 수 있습니다. 하루 한 번 작업은 정확히 365일이 되는 순간의 삭제를 보장하지 않습니다. 실행 간격과 장애로 지연될 수 있어 성공 여부를 점검해야 합니다.

정기 작업 설정 순서는 다음과 같습니다.

1. 별도의 32자 이상 무작위 `RETENTION_MAINTENANCE_KEY`를 생성합니다. 관리자 암호·export 키를 재사용하지 않습니다.
2. 같은 값을 Azure App Service 애플리케이션 설정과 GitHub `production` 환경의 동명 시크릿에 등록합니다.
3. `AZURE_WEBAPP_URL` 변수가 올바른 HTTPS 운영 주소인지 확인합니다.
4. 저장소 변수 `ENABLE_RETENTION_MAINTENANCE`를 `true`로 설정하고 `.github/workflows/data-maintenance.yml`을 수동 실행해 성공을 확인합니다. 이후 기본 브랜치에서 매일 UTC 18:17(한국 시각 다음 날 03:17)에 실행됩니다. GitHub 예약 실행은 지연·누락될 수 있으므로 엄격한 실행 주기가 필요하면 기관의 관리형 스케줄러에서 같은 API를 호출합니다.
5. 실패 알림을 수신하고 매일 실행 결과의 `deletedConsultations`, `deletedFiles`, `pendingFiles`를 확인합니다. 대기 파일이 남으면 작업은 실패로 보고되며 재실행할 수 있습니다. 이 설정은 코드 변경만으로 활성화되지 않습니다.

작업은 만료 상담, 만료 답변 캐시, 지난 날짜 질문 제한 해시, 만료 로그인 제한 해시를 정리합니다. API 사용 통계에는 질문·답변 원문을 저장하지 않습니다. 통계와 운영 로그의 별도 보존 기간은 기관이 정해야 하며 이 작업이 임의로 삭제하지 않습니다.

## 사업 삭제

권한과 본인 암호를 확인한 사업 삭제는 사업자료, 해당 자료 개정 이력, 상담, 무작위 질문, 홈페이지 연결, 승인 FAQ, 관련 충돌·답변 캐시를 함께 정리합니다. 삭제 자료를 인용하는 다른 사업의 FAQ도 정리합니다. 공통자료가 포함된 사업을 삭제하면 다른 사업에서도 해당 자료를 사용할 수 없으므로 영향을 먼저 확인합니다.

원본 파일 키는 DB 삭제와 같은 트랜잭션으로 삭제 대기열에 보관합니다. Blob 삭제가 실패해도 키를 잃지 않고 다음 정기 작업에서 재시도합니다. 아직 다른 자료가 참조하는 파일은 지우지 않습니다. 화면에 파일 삭제 대기 안내가 나오면 작업 결과를 확인합니다. 한 번에 최대 200개 파일을 처리하므로 대량 삭제는 여러 번 실행해야 할 수 있습니다.

이 기능은 앞으로 수행하는 사업 삭제에 적용됩니다. 이전 버전에서 이미 사업을 삭제해 연결 정보가 사라진 고아 파일·기록은 자동 복원·식별하지 않습니다. 기존 고아 데이터, Blob 버전·soft delete, DB 백업의 보존은 운영 담당자가 실제 저장소 정책에 맞춰 별도로 확인합니다.

## 접속기록과 CSV

로그인과 자료 export는 결과·시각·요청 식별자 등 최소 이벤트를 서버 로그로 남깁니다. 원문 암호·API 키·질문은 로그에 넣지 않습니다. 로그인 카운터는 원문 주소·아이디 대신 서버 비밀값으로 만든 HMAC을 저장하며 15분 구간이 지난 뒤 로그인 또는 정기 작업에서 삭제합니다. 역방향 프록시가 전달하는 주소 헤더의 신뢰성과 App Service 로그 수집·보존은 운영 환경에서 확인해야 합니다.

관리자별 상담 열람·CSV 다운로드·삭제의 완전한 감사기록 기능은 아직 없습니다. CSV는 브라우저에서 만들어지므로 Azure 요청 로그만으로 다운로드 사실을 확인할 수 없습니다. 필요한 기관은 행위자·시각·대상·결과를 남기는 별도 앱 감사기록을 도입해야 합니다. CSV는 공용 PC에서 내려받지 않고 기관이 정한 저장·전달·폐기 절차를 따릅니다.

## 개인정보 안내와 공개 범위

고정 안내와 전화·이메일·고유식별번호 패턴 마스킹은 입력 실수를 줄이는 장치이며 이름·주소·상세 사정을 모두 제거하지 않습니다. 기존 상담 원문은 소급하여 자동 변경하지 않습니다. 실제 개인정보 문의 담당 부서·연락처·시행일·저장 지역·국외 처리 조건·아동 이용 정책을 확인해 게시합니다.

공개하는 문의 창구는 책임자의 개인 이름 대신 실제 고충처리 담당 부서명과 전화번호·이메일로 안내할 수 있습니다. 이는 [개인정보 보호법 제30조제1항제6호](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1034292763)의 안내 범위에 따른 것입니다. 대표 연락처를 사용할 때도 해당 창구에서 개인정보 권리 요구를 실제로 접수·전달할 수 있어야 합니다.

설정의 개인정보처리방침 편집기에서 담당 부서와 전용 연락처를 입력하면 7번 문의 창구 양식을 편집할 수 있습니다. 전용 연락처를 비우면 기관 정보의 연락처를 사용합니다. 부서명이 없으면 `기관 개인정보 담당부서`로 표시하며 기관 연락처까지 비어 있으면 그 문구가 연락처 대신 표시됩니다. 이 대체 문구는 빈칸 방지 기능이므로 실제 연락 가능한 전화나 이메일을 등록한 뒤 문안을 검토·저장합니다. 새 버전 배포가 기존 게시 문안을 자동으로 덮어쓰지는 않습니다.

사용하지 않는 초기 테스트 사이트는 소유 서비스에서 폐쇄·비공개 처리해야 합니다. 문서에서 주소를 지우는 것만으로 사이트는 중지되지 않습니다. 제출 저장소의 ZIP 해제·공개 범위와 기존 커밋 이메일 변경은 별도 작업이며 운영 저장소의 코드 변경이 이를 대신하지 않습니다.
